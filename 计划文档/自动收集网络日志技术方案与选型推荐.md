# DialogLogShowManager 框架无关型 App 网络日志自动收集方案（HTTP & HTTPS）

## 1. 设计核心原则

1. **框架无关（Framework-Agnostic）**：
   无需关心或假设宿主 App 使用了什么网络框架（无论 OkHttp、HttpURLConnection、Volley、HttpClient、Cronet、WebView，还是 C/C++ 自研 Socket），SDK 必须在系统更底层实现统一捕获。
2. **协议双兼容（HTTP & HTTPS）**：
   必须同时覆盖明文 **HTTP** 协议（80 端口流）与经过 TLS 加密的 **HTTPS** 协议（443 端口明文流），且不能依赖用户在设备端安装根证书。

---

## 2. 框架无关与 HTTP/HTTPS 拦截技术原理

在 Android 系统中，无论使用什么网络框架，所有 HTTP / HTTPS 流量在传输前都必然经过系统底层关口。根据拦截粒度不同，有两种彻底框架无关的通用捕获方案：

```
                               ┌─────────────────────────────────────────────────────────────┐
                               │                 外部开发者 App (任意网络框架)                 │
                               └──────────────┬──────────────────────────────┬───────────────┘
                                              │                              │
                                   (Java 层网络调用)                (Native / C++ / WebView)
                                              │                              │
                                              ▼                              ▼
┌──────────────────────────────────────────────────────────┐ ┌──────────────────────────────────────────────┐
│ 【方案 A】Java 运行时全局拦截                             │ │ 【方案 B】Native PLT 全局 Hook (终极方案)       │
│                                                          │ │                                              │
│  HTTP  ───► SocketImplFactory                            │ │  HTTP  ───► Hook libc.so (send / recv / write│
│             (捕获普通 Socket 字节流)                      │ │             / read)                          │
│                                                          │ │                                              │
│  HTTPS ───► SSLSocketFactory / SSLContext                │ │  HTTPS ───► Hook libssl.so (SSL_read /       │
│             (捕获 TLS 握手解密后的明文流)                │ │             SSL_write)                       │
└──────────────────────────────────────────┬───────────────┘ └──────────────────────┬───────────────────────┘
                                           │                                        │
                                           └───────────────────┬────────────────────┘
                                                               │
                                                               ▼
                                              ┌─────────────────────────────────┐
                                              │   DialogLogShowManager 统一解析  │
                                              │   (HTTP 报文解析与可视化展示)     │
                                              └─────────────────────────────────┘
```

---

### 方案 A：Java 运行时全局代理（覆盖所有 Java 层的 HTTP & HTTPS）

此方案无需依赖任何三方框架，完全基于 JVM / Android Java 运行时的系统接口代理实现：

#### 1. HTTP 明文请求捕获
- **技术机制**：`java.net.Socket.setSocketImplFactory(...)`
- **原理**：
  在 SDK 初始化时注入全局 `SocketImplFactory`。当 Java 层建立普通 HTTP 的 Socket 连接时，代理 `SocketImpl` 的 `InputStream` 和 `OutputStream`，直接提取原始 HTTP 请求头与响应体。

#### 2. HTTPS 加密请求捕获
- **技术机制**：全局 `SSLSocketFactory.setDefault(...)` 与代理 `SSLContext`
- **原理**：
  HTTPS 流量在 Socket 传输层是加密密文，但**在 TLS 握手层解密后/加密前是明文**。
  通过替换全局 `SSLSocketFactory`，在 `SSLSocket` 创建的输入输出流上挂载 Delegate。数据被 TLS 加密前（发送时）和解密后（接收时），捕获其 HTTP 明文字符串。

#### 3. URL 链接兜底
- **技术机制**：`URL.setURLStreamHandlerFactory(...)`
- **原理**：
  拦截所有 `java.net.URL` 的连接创建，返回统一的 Log 代理 Connection，作为 Java 标准库请求的补充防护。

- **方案 A 评估**：
  - **优点**：纯 Java 实现，无需引入 C/C++ SO 库；兼容性好；100% 独立于外部网络框架。
  - **局限**：仅覆盖 Java/Kotlin 运行时的网络请求，无法捕获 Native 独立网络库（如 Chromium Cronet）或部分 Native 渲染的 WebView。

---

### 方案 B：Native PLT 全局 Hook（终极方案：100% 覆盖所有 HTTP & HTTPS）

如果要求做到 **“任何网络框架 + 任何 C/C++ Native 库 + WebView 零死角捕获”**，Native 层的系统函数 Hook 是最彻底的解法。

#### 1. HTTP 明文请求捕获 (Native 80 端口)
- **技术机制**：Hook C 标准库 `libc.so` 的 `connect` / `send` / `recv` / `write` / `read` 函数
- **原理**：
  通过 PLT Hook 动态拦截网络 Socket 读写。通过判断 Socket 端口（80 端口）及 HTTP 报文特征（`GET /`, `POST /`, `HTTP/1.1`），实时捕获 HTTP 明文。

#### 2. HTTPS 加密请求捕获 (Native 443 端口)
- **技术机制**：Hook 系统 SSL 库 `libssl.so` / `libcrypto.so` 中的 `SSL_read` 与 `SSL_write` 函数
- **原理**：
  Android 系统中不论 Native 层的 Cronet、libcurl、BoringSSL 还是 WebView 内核，在传输 HTTPS 时，最后都必然调用 SSL 动态库的 `SSL_read`（读取解密后的数据）与 `SSL_write`（写入加密前的数据）。
  Hook 这两个 API，就能在不需要解密密文、不需要安装根证书的前提下，**捕获 100% 进程内发出的 HTTPS 明文日志**。

- **方案 B 评估**：
  - **优点**：真正的 **100% 全量覆盖**，彻底无视任何网络框架与实现语言（Java/C++/Rust）。
  - **局限**：需要集成轻量级 Native Hook 库（如开源的 `shadowhook` / `xhook`）；需在 SDK 内增强 HTTP/1.1 与 HTTP/2 报文的流式解包能力。

## 3. HTTP 与 HTTPS 统一解析引擎设计

因为底层捕获到的是**原始 HTTP/HTTPS 协议明文数据流**（非上层框架封装好的对象），SDK 内部需要内置一个轻量级的 **HTTP 报文解析器 (Stream Parser)**：

```
[原始数据字节流 (HTTP / HTTPS)] 
         │
         ▼
 ┌─────────────────────────────────────────────────────────────┐
 │ SDK 内部轻量级 HTTP 状态机解析器                              │
 ├─────────────────────────────────────────────────────────────┤
 │ 1. 行解析: 提取 Method(GET/POST)、Path、Status Code(200...) │
 │ 2. 头解析: 提取 Content-Type, Content-Length, Headers        │
 │ 3. 体解析: 根据 Content-Type (JSON/Form) 提取 Body 字符串    │
 └──────────────────────────────┬──────────────────────────────┘
                                │
                                ▼
              ┌──────────────────────────────────┐
              │ 生成 HttpLogData 并交付界面展示   │
              └──────────────────────────────────┘
```

## 4. 推荐落地策略

针对**“无视网络框架”**且**“兼容 HTTP/HTTPS”**的需求：

### 阶段 1：纯 Java 运行时代理（快速落地）
- 实现 `SocketImplFactory`（负责 HTTP）+ `SSLSocketFactory`（负责 HTTPS）。
- 零代码侵入，纯 Java 实现，适配所有使用 Java 层的网络框架。

### 阶段 2：集成 Native Hook（全量无死角）
- 引入 `shadowhook`，Hook `SSL_read` / `SSL_write`（针对 HTTPS）以及 `send` / `recv`（针对 HTTP）。
- 补充覆盖 Native 库、Cronet 及 WebView 网络流量。
