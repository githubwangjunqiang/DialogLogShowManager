## 一、总则

### 1.1 目标

- 轻量级键值数据优先使用 MMKV
- 结构化数据、复杂查询、事务场景优先使用 Room

### 1.2 优先复用现有封装与固定命名

- 必须优先复用项目现有存储封装，禁止重复造轮子
- 只有在项目没有现成封装时，才按本技能约定的固定命名生成代码
- 默认固定命名：`MMKVUtil`、`AppDatabase`、`XXXDao`、`XXXRepository`
- 若项目已有明确命名规范，应优先遵循项目现有命名

## 二、MMKV 规则

### 2.1 适用与不适用

- 适合：Token、登录态、开关配置、用户偏好、临时状态、少量简单对象
- 不适合：复杂结构化数据、联表查询、分页筛选排序、大体积对象、强事务数据

### 2.2 初始化与命名

- 初始化必须在 `Application` 阶段完成，并集中管理
- 存储路径应优先使用应用私有目录
- Key 必带明确业务域前缀防冲突
- 业务域内命名风格必一致，禁止含义不明的短 Key
- Key 必集中放入常量池（如 `LocalStorageKeys`），禁止散落定义

示例：

- `user_token`
- `setting_theme_mode`
- `cache_last_sync_time`

### 2.3 存储、读取、清理

- 基础类型和 `Set<String>` 可直接存取
- 对象应先序列化后再存为字符串
- 对象序列化优先复用项目现有方案；若项目没有统一方案，默认使用 JSON
- JSON 序列化必沿用现有库，禁止引入新体系
- 对象结构应尽量简单、稳定、字段变化可控
- 复杂嵌套对象和大对象不应作为默认方案；优先拆分、缓存或改用数据库
- 读取逻辑应考虑旧版本数据兼容问题
- 必须支持按单个 Key 删除
- 必须支持按业务域清理
- 退出登录时可清理与当前用户相关的数据
- Token、凭证、会话信息等敏感数据不应裸存
- 如果必须存储敏感信息，应优先考虑加密方案

## 三、Room 规则

### 3.1 适用与不适用

- 适合：结构化业务数据、用户/文章/消息/订单等实体、复杂查询、事务、长期持久化、离线可用数据
- 不适合：简单配置项、单值读写、无需查询的数据、临时状态缓存

### 3.2 实体、DAO、数据库

- 数据库版本必须可管理
- 禁止默认使用破坏性迁移
- 版本升级应优先考虑可控迁移策略
- 数据库实例应统一管理，避免重复创建

### 3.3 Repository、转换、线程

- Repository 只负责统一数据访问入口
- 复杂类型需要明确转换策略
- 如果使用类型转换器，应保证可逆性和稳定性
- 禁止使用易丢数据的转换方式
